# Browser runtime lab (isolated)

This is a **manual, loopback-only comparison** of ordinary Playwright Chromium and CloakBrowser. It is not imported by any production scraper, has no Tailscale exit-node route, and makes no requests to HiringCafe or other third-party job sites. CloakBrowser's own binary has source-level fingerprint changes; this lab does not implement CAPTCHA solving, cookie transfer, proxies, or challenge handling.

## Run

1. Obtain a CloakBrowser license through the vendor's official process. Add it **directly in GitHub** at the Scoutgrid repository's Settings → Secrets and variables → Actions → New repository secret. Name it `CLOAKBROWSER_LICENSE_KEY`. Do not paste the key into a chat, commit, issue, or workflow input.
2. Dispatch the **Browser runtime lab (local fixture only)** workflow manually — GitHub UI: Actions → "Browser runtime lab (local fixture only)" → Run workflow; CLI: `gh workflow run browser-lab.yml`. `CLOAKBROWSER_LICENSE_KEY` is read from repository secrets only inside the **Strict CloakBrowser preflight** and **CloakBrowser on same loopback fixture** steps' own `env:` blocks — never as a command-line argument, never echoed, never a workflow input. Ordinary Playwright runs without that secret.
3. Read the **Strict CloakBrowser preflight** step's output first. It runs `browser-lab/preflight.mjs`, which resolves to exactly one of five statuses, checked in this order, and never attempts a later stage once an earlier one has already decided the outcome:
   - `license_missing` — no `CLOAKBROWSER_LICENSE_KEY` at all. Expected without the secret; not a failure. Install/launch are never attempted.
   - `install_failed` — the license is present, but downloading/installing the Pro binary itself threw (network, signature verification, disk, vendor outage). Launch is never attempted.
   - `binary_missing` — install reported success, but the binary still isn't on disk afterward. Launch is never attempted.
   - `launch_failed` — the binary is installed, but actually starting the browser failed (crash, a license denial surfacing at launch time, etc.).
   - `ok` — license present, binary installed, browser launched and closed cleanly. Only this status runs the CloakBrowser smoke step.
4. **Acceptance criteria** for the workflow run as a whole:
   - Without `CLOAKBROWSER_LICENSE_KEY` configured: preflight status is `license_missing`, the job summary shows CloakBrowser as **SKIPPED** (not failed, not passed), and the overall job **succeeds** — a missing license is not a workflow failure.
   - With `CLOAKBROWSER_LICENSE_KEY` configured: preflight status must be `ok` for the run to count as a genuine compatibility pass. Any of `install_failed`/`binary_missing`/`launch_failed` makes the **"Fail the job on a real preflight failure"** step exit 1 — the job fails loudly rather than silently reporting SKIPPED for a real problem.
   - When preflight is `ok`, the CloakBrowser smoke step must itself report `exit_code=0` and a `classification` of `ok` with a non-zero job count against the loopback fixture — matching Playwright's own result on the identical page.
5. Review the two smoke-step logs for the `ok` path. Each prints the response status, DOM classification, parsed fixture-job count, browser-startup time (`startupMs`), navigation time (`navigationMs`), DOM parse time (`domParseMs`), and process `exit_code`. The GitHub job summary states each runtime's outcome, and — when preflight did NOT reach `ok` — which of the four non-`ok` statuses explains why, instead of a single generic "SKIPPED". Both runtimes visit the identical page served at a randomized `127.0.0.1` port by `browser-lab/smoke.mjs`.

Local ordinary-browser check after `npm ci --prefix browser-lab --ignore-scripts`: `browser-lab/node_modules/.bin/playwright-core install chromium`, then `BROWSER_LAB_RUNTIME=playwright node browser-lab/smoke.mjs`. For a licensed local-only preflight+comparison, run `CLOAKBROWSER_LICENSE_KEY=<key> node browser-lab/preflight.mjs` (never pass the key as a `--flag`), then, only once it prints `"status": "ok"`, `BROWSER_LAB_RUNTIME=cloakbrowser node browser-lab/smoke.mjs` with the same environment variable set. Supply the key via your own shell environment or the vendor's secure login flow, never hardcoded in a script or committed anywhere.

## If a future target permits the intended automation

Obtain and document the target's permission/access terms first. Run a separate approved-site test, compare reliability and job-data integrity, and review the vendor binary/dependency and license implications. Only then propose a **separate, reviewed change** that explicitly selects a runtime for that permitted target. The present adapter has no production import or `BROWSER_LAB_RUNTIME` wiring in `scrape-hiringcafe.py`, `fetch-hiringcafe-feed.mjs`, or their workflows — `browser-lab/preflight.mjs` likewise only installs and starts the vendor's own binary against nothing; it never navigates anywhere, let alone HiringCafe. Browser compatibility on loopback does not imply HiringCafe accessibility or authorize its search-path crawling.

## HiringCafe integration-readiness report (2026-11-13)

Confirmed real, licensed CloakBrowser runs in GitHub Actions (runs `43448215257` and `43449466460`, commit `444db45c`): preflight reaches `ok` (binary installs, Ed25519-signature-verified, launches, closes), the loopback smoke test reports `status:200`/`classification:"ok"`, and a new fixture shaped exactly like the page `scrape-hiringcafe.py` parses (`__NEXT_DATA__` with `ssrHits`/`apply_url`) extracts identically through CloakBrowser and Playwright.

### Complete
- `browser_runtime.py`'s `BrowserRuntime`/`BrowserSession` interface — stable, tested with fakes and real patchright (`test/hc-browser-timeout-config.test.mjs`, `test/hc-real-browser-smoke.test.mjs`).
- `browser-lab/adapter.mjs`'s CloakBrowser launch path — now verified against the vendor's real binary, not just mocks (`test/browser-lab-adapter.test.mjs` + the real runs above).
- Strict preflight distinguishing `license_missing`/`install_failed`/`binary_missing`/`launch_failed`/`ok` — verified for real in CI (`test/browser-lab-preflight.test.mjs` + the real runs above).
- JS-side page-API compatibility against an HC-shaped fixture — verified for real (`test/browser-lab-hc-shaped-compat.test.mjs`): a CloakBrowser-launched Playwright `Page` exposes `goto`/`waitForSelector`/`title`/`content`/`close`, the exact method set `BrowserSession` requires, modulo language.

### Gaps — what remains blocked before any production wiring
1. **Language mismatch (the actual blocker).** `scrape-hiringcafe.py` is Python, calling `patchright.sync_api` directly. `cloakbrowser` is an npm package (`dist/*.js`, Playwright-core based) with no Python bindings at all. There is no `pip install cloakbrowser`. A production `CloakbrowserRuntime(BrowserRuntime)` cannot simply `import cloakbrowser` the way `PatchrightRuntime` imports `patchright`. The only structurally sound bridge is: a Node child process launches CloakBrowser with `--remote-debugging-port=<port>` (via `args` in `buildLaunchOptions`'s result), Python's own `patchright`/`playwright` then calls `chromium.connect_over_cdp(f"http://127.0.0.1:{port}")` to drive the already-launched, already-patched browser, and the resulting `Page`/`BrowserContext` get wrapped in something very close to the existing `PatchrightSession` (its `goto`/`content`/`title`/`wait_for_selector` methods would likely work unchanged against a CDP-attached page — only `open()`/`close()` need new child-process lifecycle code). **This bridge does not exist and has not been attempted** — building and testing it is new, non-trivial work, not a config change.
2. **Binary footprint and licensing are a real operational difference, not just a flag.** `PatchrightRuntime` uses whatever system Chrome is already on the runner/box (`channel="chrome"`). CloakBrowser ships and license-gates its *own* patched Chromium — the real run above downloaded 206 MB, verified an Ed25519 signature and SHA-256 checksum, and reported `"CloakBrowser free: 1 concurrent session."` on this license. `fetch-hiringcafe-feed.mjs` currently launches a **fresh browser process per query, sequentially** (with a 3s pause between launches specifically to avoid a profile-lock race — see `fetchViaPatchright`), which a 1-session free tier could tolerate, but it leaves zero headroom for any future concurrency without a paid seat increase.
3. **Compatibility was proven only against a loopback fixture.** Nothing here demonstrates CloakBrowser's stealth/fingerprint patches actually change the outcome against HiringCafe's real Cloudflare challenge — and per the project's standing rule and this task's own constraint, that is **not to be tested**. A page-API match on loopback says the plumbing *could* carry data if a future target were reachable; it says nothing about HiringCafe specifically.

### Documented, permitted ways to retrieve HiringCafe data (evaluated, not yet pursued)
- **No general public REST API.** Independent confirmation (a competing jobs-API vendor's own comparison page) states HiringCafe does not offer one and its terms don't invite scraping.
- **An official, documented read-only connector for AI assistants does exist**: `hiringcafe.com/documentation` lists a "HiringCafe Job Search Claude Connector" and a ChatGPT equivalent — i.e. HiringCafe's own sanctioned MCP-based integration. An unofficial PyPI package (`hiringcafe-cli`) is built on top of it and documents its real limits: **at most 10 jobs per search, at most one job per company, no pagination or filters yet, and a rate limit** — this is a genuinely permitted path, but far too low-volume/low-fidelity to replace the saved-search HTTP/browser scrape this project previously ran (hundreds of jobs/day).
- **A historical informal offer of direct API access** exists from a 2024 Reddit post by a HiringCafe team member inviting interested developers to email `ali@hiringcafe.com`. This is the only lead toward real-volume, officially sanctioned access; it requires the user to make that outreach directly — not something to act on autonomously.
- **Recommendation**: do not wire CloakBrowser (or any other browser runtime) against HiringCafe's actual search pages. The two realistic forward paths are (a) the user emailing HiringCafe for real API/partner access, or (b) adding the documented Claude/ChatGPT connector as a low-volume, clearly-labeled supplementary source if its ~10-jobs-per-search cap is acceptable — both outside this lab's scope and requiring a separate, reviewed change.
